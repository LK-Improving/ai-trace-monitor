# Phase 3 W30–W32：G3 试点验收与回滚计划

日期：2026-10-03
状态：实现与隔离本地端到端联测已通过；真实 Staging、项目方用户验收及发布回滚演练尚未执行。

## 阶段目标

完成 G3 / MVP 上线前的真实数据链路验证，并明确本地验收与外部试点之间的证据边界。任何本地演示、mock 数据或仅有 Trace ID 相同的请求都不能单独证明前端事件与服务端 Span 已组成可查询的父子树。

## 本轮数据关联契约

- 浏览器一次页面导航生成一个安全的 `browser.navigation` 根 Span 与稳定 `traceId`。
- Web Vital、JavaScript Error、Promise rejection 等浏览器观测 Span 使用相同 `traceId`，并以导航 Span 的 `spanId` 作为 `parentSpanId`。
- 同源业务 HTTP 请求传递 `x-trace-id` 与 `x-parent-span-id`；API 仅接受单个 32 位小写十六进制父 Span ID，并把它写为 `http.server` 根 Span 的 `parentSpanId`。原有 `x-trace-id` 行为保持兼容。
- 浏览器到服务端的 Trace 上下文代理只转发白名单头；浏览器不接触项目写入密钥或平台管理员令牌。跨域请求不传播上下文。
- 页面地址、异常原文、请求体、Prompt/Response、凭证不得因父上下文接入而扩大采集范围。

## 本轮实现与验收证据

- 实际浏览器生成 `browser.navigation` 根 Span；3 个 Web Vital、同源 503、合成 JavaScript Error 与 Promise rejection 均以该 Span 为父级并通过本地 Relay 上报。页面显示 7 条浏览器事件，SDK 报告 API 内存排队成功、失败/丢弃均为 0，脱敏 canary 未发现。
- Playwright 从同一页面请求隔离项目的指标 API，BFF 返回 HTTP 200。Collector 从本轮随机 topic 消费；ClickHouse 中最终查到 8 个同 Trace Span，API `http.server` Span 的父 ID 指向浏览器导航根；Trace Detail 返回单根、无孤儿树。
- `output/playwright/w30-g3-result.json` 记录通过结果；`output/playwright/w30-g3-cleanup-result.json` 记录临时项目、ClickHouse 行、Kafka topic/group 与子进程清理通过。两个文件是本机验收产物，不是 Staging 证据。
- API 测试 199 通过、2 个可选集成测试跳过；Collector 25 通过、1 个可选集成测试跳过；Web 全部测试 99/99；Relay 15/15。`pnpm typecheck` 与 `pnpm build` 均通过。
- 本地验收启动时出现一次 Node `TimeoutNegativeWarning`；独立 API/Collector 均就绪且链路通过，但警告来源未定位。它不等同于功能失败，仍需另行追因。

## P0 阻断项

对照需求文档的 P0 功能表与第 8 节验收标准，本轮发现以下数据生命周期缺口，不能将 G3/MVP 标记为通过：

1. 项目 API 可写入 `retentionDays`，但项目设置页明确未提供保留策略读取/更新；ClickHouse 当前表 DDL 使用全局固定 30 天 TTL，没有按项目配置执行。
2. 总览/AI 指标从 Trace 明细表实时聚合。明细 TTL 删除后，没有持久化聚合表可继续提供历史指标，与验收标准“聚合指标不因明细清理而失效”不符。

证据位置：`apps/api/src/projects/projects.service.ts`、`apps/web/src/pages/Pages.tsx` 的 retention 页、`infra/clickhouse/init/001-trace-spans.sql`、`apps/api/README.md` 的指标边界说明。当前通过证据只覆盖浏览器与 API Trace 的联合入库/查询，不覆盖上述保留与聚合要求。修复方案需要明确最小保留周期、按项目 TTL 的存储策略和聚合幂等/迟到数据语义；在这些策略确定前，不更改 ClickHouse 表结构或宣称历史指标可跨 TTL 保留。

## 隔离本地联测方法

前置条件：本地 Compose 依赖服务健康、Contracts/API/Collector/Web 已构建、Playwright CLI 可用。验收脚本要求显式开启 `TRACE_OPS_RUN_INTEGRATION=1`，只接受 loopback 数据库、Kafka 和 ClickHouse 地址。它会为每次运行创建随机 Kafka topic、consumer group、临时项目/服务/写入密钥、独立 API/Collector/Web 端口；只把密钥放在可信 Node/Vite 服务端环境中。运行结束会停止本次子进程，并删除本次 ClickHouse 数据、PostgreSQL 项目和 Kafka 临时资源；不会重启或删除已有 Compose 容器/数据卷，也不会写入共享 `ai-spans` topic。

```powershell
$env:TRACE_OPS_RUN_INTEGRATION = '1'
pnpm acceptance:w30:g3
```

脚本输出临时 SDK 页面 URL 和 project ID 后，在另一个终端用 Playwright CLI 打开页面。按最新 `snapshot` 返回的元素引用依次启动 SDK、开启本地 Relay，并触发同源 503、合成 JS Error 和 Promise rejection；随后用 `eval` 从该页面请求指标 API，例如：

```powershell
npx --yes --package @playwright/cli playwright-cli --session w30-g3 eval "fetch('/api/v1/metrics/overview?projectId=<脚本输出的 ID>&environment=dev&range=24h').then(r => r.status)"
```

这确保真实 API 请求通过本地管理代理并带上 Trace 上下文。等待 SDK 显示 API 内存队列已接收后，在运行验收脚本的终端输入 `verify`，检查 ClickHouse 入库和 Trace Detail 单根/无孤儿树；最后输入 `finish` 清理。

脚本结果仅证明这台机器上隔离环境的集成链路，不代表项目方 Staging 数据边界审批、真实用户验收或发布回滚演练。

## 回滚演练步骤（仅在隔离 Staging 执行）

1. 记录当前应用版本、配置版本、Kafka/ClickHouse 状态和测试 Trace ID；仅使用合成数据。
2. 按发布方案关闭浏览器 SDK/Relay 上报，并将 API `SERVER_TRACE_ENABLED` 设为 `false`；确认普通业务 API 可用且不再产生新 Span。
3. 恢复上一版应用与配置，检查 API、Collector、Kafka 消费和 ClickHouse 写入状态。
4. 再次发起一条合成请求，确认旧版本行为、错误码、鉴权和队列状态符合预期；检查是否存在凭证或敏感内容泄漏。
5. 留存步骤、耗时、观察结果及清理证明，由试点负责人签收。

当前仓库的 `compose.yaml` 管理 PostgreSQL、Kafka、ClickHouse、Mailpit 等依赖；应用本身以开发进程启动，本仓库尚未提供可供 Staging 回退的应用镜像版本/发布制品。因此本地功能开关检查不等于真实发布回滚演练。
