# Phase 3 W28–W30：平台健康与容量验收

日期：2026-10-03
范围：平台运行健康、采集端队列容量、Kafka lag、Collector 消费/ClickHouse 写入情况、ClickHouse 查询延迟、本地负载基线与故障演练。

## 实现范围

- `GET /api/v1/ops/health` 由现有平台管理员令牌保护；返回固定 DTO，不包含凭证、SQL、原始依赖错误或 Span 内容。管理页仅通过本地同源管理代理调用，不在浏览器持有管理员令牌。
- API 并发探测 PostgreSQL、Kafka、Collector 与 ClickHouse。Kafka 返回 topic 各分区 lag；未提交 offset 按分区起点计算。探测超时或 offset 不可得时标记 `degraded` / `unavailable` 并将数值置为 `null`。
- Collector 仅在 `127.0.0.1:3011/internal/ops/health` 暴露 GET 健康快照。响应字段严格校验并限制大小；运行状态和计数来源于 Collector 实际批处理、ClickHouse 插入、无效消息分类和 Kafka commit 路径。
- 控制台提供平台级运维页，显示依赖状态、Kafka 分区 lag、Collector 运行计数、API Span 队列 Span/字节容量、ClickHouse ping 和进程内近 5 分钟查询延迟，每 30 秒刷新；当前项目、环境和时间筛选不作用于平台级视图。
- PostgreSQL 健康探测使用独立、单连接且设有超时的 pool；ClickHouse 查询只保留有界的延迟样本，不保存 SQL 文本。

## 指标口径与限制

- API 队列和 Collector 计数是单进程生命周期累计值，进程重启归零；ClickHouse 延迟窗口是单 API 进程近 5 分钟最多 5,000 个样本，重启清空。多副本时当前接口不汇总各副本，也不是长期时序存储。
- Kafka 故障时 API 上报采用 best-effort 有界内存队列；Kafka 恢复前可能丢 Span。当前已验证的是快速返回、容量拒绝和丢弃计数，不是持久化缓冲或无损投递。
- 40/4 与 200/20 是本机健康接口读取基线，不是生产压测，不代表真实业务写入吞吐、持续负载、尾延迟 SLA 或基础设施容量上限。
- ClickHouse 故障演练验证 Collector offset 与恢复链路；不代表 Kafka 集群容灾、ClickHouse 副本/集群恢复或跨机房演练。
- Collector 在 `pnpm dev` 启动时曾输出 Node `TimeoutNegativeWarning`，但紧接着成功订阅 `ai-spans`，真实健康快照为 running。本轮未定位该警告来源；它不影响本次通过结果，但仍应单独追因。
