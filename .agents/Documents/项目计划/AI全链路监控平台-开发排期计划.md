# AI 全链路监控平台开发排期计划

> 版本：V0.1（排期草案）  
> 编制日期：2026-09-25  
> 计划口径：相对周数；项目启动并确认资源后，以 T0 为第 1 周  
> 依据：需求设计文档《AI 全链路监控平台》、用户提供的架构图和落地路线图、当前仓库实现情况

## 1. 排期目标与口径

本计划以图片中的四阶段路线为时间框架，并以需求文档的 P0 / P1 / P2 优先级确定交付边界。前三阶段覆盖首个可用版本，预计 **20–32 周（约 5–8 个月）**；第四阶段为持续演进，不纳入 MVP 上线门槛。

| 阶段 | 图片中的规划 | 本计划时间 | 阶段目标 |
| --- | --- | --- | --- |
| Phase 1 | 前端监控 SDK + 基础存储 | 4–8 周（1–2 个月） | Web Trace ID / 基础采集、Kafka 与 ClickHouse 数据通路、基础指标页 |
| Phase 2 | 服务端 APM + AI 链路追踪 | 8–12 周（2–3 个月） | TraceRecorder 覆盖服务端、RAG / LLM Span 可串联、Trace 查询和 AI 指标 |
| Phase 3 | 全链路打通 + 告警体系 | 8–12 周（2–3 个月） | 完成端到端 Trace、告警处理与通知、试点验收和上线准备 |
| Phase 4 | AI 根因分析 + 智能运维 | 持续迭代 | 根因建议、异常辅助处置、成本优化等增强能力 |

排期按 1 个月约 4 周估算，包含开发、联调和验收时间，不等同于固定日历日期。项目当前没有确认团队人数、正式启动日和试点应用，故先用相对周数排计划；资源变化时按相同阶段门重新估算，不压缩安全与数据校验工作。

下文逐周任务按保守基线展开：Phase 1 / 2 / 3 分别取 8 / 12 / 12 周，合计 32 周。20 周属于压缩目标，需要阶段实际分别控制在 4 / 8 / 8 周、关键接口并行稳定且测试资源到位；未确认资源前不把压缩周期作为承诺。

## 2. 当前仓库基线

当前已具备工程骨架和可评审的 mock 控制台，不代表端到端监控能力已经交付。正式接入和真实数据验证属于后续排期。

| 模块 | 当前情况 | 排期处理 |
| --- | --- | --- |
| Web 控制台 | 总览、Trace 列表/详情、AI 链路、告警、项目设置、接入文档已用 mock 数据搭建；交互不落库 | Phase 1 起逐页替换为 API 数据，保留 mock 作为开发回退方案 |
| 共享契约 | `packages/contracts` 已有 TraceSpan / SpanEvent 校验、ClickHouse 行转换和敏感属性过滤 | Phase 1 固化 schema 版本、Header、错误码和兼容策略 |
| API | NestJS 启动、健康检查和 PostgreSQL ping 已有；尚无项目管理、鉴权、Span 上报及查询 API | Phase 1 完成最小项目/服务/凭证和上报能力；Phase 2 完成查询 API |
| Collector | Kafka 消费与 ClickHouse 批量写入骨架已存在；尚未完成实际环境联调、死信和完整自监控 | Phase 1 验证真实写入及故障边界，后续补齐重试、积压和运行指标 |
| 数据库与容器 | Compose 已定义 PostgreSQL、Kafka、ClickHouse；初始化 SQL 已有项目配置表和 30 天 TTL 的 `trace_spans` | Phase 1 以该 Compose 作为本地集成环境，表结构变更走版本化迁移 |
| 业务 SDK / 数据链路 | 尚无可供接入方使用的正式 SDK，也未验证浏览器到 API、Kafka、Collector、ClickHouse 的完整链路 | 作为 Phase 1 首要交付，不把已有骨架视为验收通过 |

## 3. 范围与排期原则

1. **先闭环 P0**：项目/服务、Trace 透传、Span 记录、异步上报、Collector 入库、Trace 查询与执行树、LLM / RAG 核心指标、基础告警、隐私默认关闭原文采集。
2. **以图片的数据流为关键路径**：Web SDK → API / TraceRecorder → Kafka `ai-spans` → Collector → ClickHouse → 查询 API → 控制台；先端到端验证，再扩展指标和界面。
3. **第三方服务由一个 Compose 工程统一管理**：开发环境中的 PostgreSQL、Kafka、ClickHouse 继续由仓库根目录 `compose.yaml` 管理；Qdrant 与模型服务属于接入方依赖，不默认加入本平台 Compose。
4. **业务请求不能等待监控写入**：Producer 异步投递；Kafka 暂不可用时按需求实现有界降级策略；Collector 失败时不得提前提交 Kafka offset。
5. **敏感数据默认不出域**：Prompt、Response、用户输入和文档正文默认不采集；任何查看原文的后续能力都需要显式项目策略、脱敏和权限门槛。
6. **P1 / P2 不阻塞 MVP**：图片路线图提到的 SourceMap、Issue 聚合、Prompt 管理、评估数据集等，按需求文档优先级拆为增强项，不作为首个可用版本的前置条件（见第 7 节）。

## 4. 主排期与阶段门

### Phase 1：前端 SDK 与基础存储（第 1–8 周）

目标：形成第一条可靠、可查询的监控数据路径，并建立最小项目接入体验。

| 周次 | 工作项 | 主要交付物 / 验收点 |
| --- | --- | --- |
| W1 | 对齐 Span 字段、`schemaVersion`、环境命名、`x-trace-id` 规则、项目密钥边界；启动 Compose 集成环境 | 接口契约定稿；本地 PostgreSQL / Kafka / ClickHouse 健康检查通过；建立迁移与测试约定 |
| W2–W3 | API 项目、服务、环境和项目密钥最小管理；密钥只存 Hash；浏览器 SDK 生成或透传 Trace ID | 新建项目/服务的最小 API；浏览器请求能携带 `x-trace-id`；服务端缺少 Header 时可生成并返回 Trace ID |
| W3–W4 | 浏览器 SDK 采集 Web Vitals、JS / Promise / 请求异常；敏感字段过滤与采集开关 | 测试页面可以产生带 Trace ID 的前端事件；默认不上传 Prompt / Response 和用户原文 |
| W4–W6 | Span 上报 API、schema 校验、Kafka Producer；配置 `ai-spans`、以 `traceId` 为 key；实现非阻塞发布及有界降级 | 合法 Span 进入 Kafka；非法消息有计数和可追踪错误；Kafka 不可用时业务接口仍可返回 |
| W5–W7 | Collector 批量消费、校验、ClickHouse 批量写入；完善 offset 提交顺序、重试与异常消息处理 | 一条测试 Span 可从 Kafka 入 ClickHouse；写入失败不丢消息；TTL 为 30 天并有验证记录 |
| W7–W8 | 接入基础总览查询、服务健康与错误列表；将首屏 KPI / 服务数据接到 API；集成回归 | **阶段门 G1**：在本地环境完成 SDK → API → Kafka → Collector → ClickHouse 的真实数据闭环，并能从页面看到基础运行数据 |

**Phase 1 不包含**：完整 Trace 执行树、模型价格管理、复杂告警规则、Prompt 内容采集。优先保证数据结构、安全边界和传输可靠性。

### Phase 2：服务端 APM 与 AI 链路追踪（第 9–20 周）

目标：将一次请求中的服务端、RAG、LLM 和 Tool 操作按 `traceId / parentSpanId` 还原，并支持检索分析。

| 周次 | 工作项 | 主要交付物 / 验收点 |
| --- | --- | --- |
| W9–W11 | 实现服务端 TraceRecorder：`start / set / setUsage / end`，父子 Span、状态、耗时和异常记录；定义 NestJS 接入方式 | API 请求产生 `http.server` root Span；异步发布不阻塞业务响应；服务、环境、Trace ID 字段一致 |
| W11–W14 | 接入 OpenAI 兼容调用和 RAG 调用埋点；记录模型、Token、TTFT、错误分类、topK、sources、召回/重排耗时 | 同一请求至少含 `http.server`、`rag.retrieve`、`llm.generate` Span；模型 usage 与 RAG 属性在 ClickHouse 可查 |
| W13–W16 | 实现 Trace 列表、详情  API 和 ClickHouse 查询：按项目、环境、Trace ID、服务、状态、时间分页过滤 | API 覆盖需求文档 `/traces` 与 `/traces/:traceId`；执行树父子关系、耗时和错误信息完整 |
| W15–W18 | 建设聚合查询与 AI 链路指标：请求量、错误率、P50/P95/P99、Token、模型延迟、RAG 成功/空召回 | 常用时间范围的指标查询满足目标；列表查询 P95 < 2 秒、总览查询 P95 < 3 秒（测试数据集与口径需记录） |
| W18–W20 | 将 Trace 和 AI 页面从 mock 切到 API；补齐项目 / 环境 / 时间筛选、空态、加载与错误处理 | **阶段门 G2**：接入示例应用后，可以从 Trace ID 看到完整 Span 树，并定位慢 Span、模型用量和 RAG 结果 |

**阶段门 G2 的端到端验收**：浏览器生成并传递 Trace ID，一次包含服务端处理、RAG 检索和 LLM 调用的测试请求可回查服务端执行树；模型错误或业务异常可以关联到原 Trace；敏感原文仍按默认策略屏蔽。此阶段验证请求 ID 贯通，不将前端性能/异常事件联查或跨服务 parent 上下文认定为已完成。

### Phase 3：全链路集成与告警（第 21–32 周）

G3 需单独验收真实 Web 性能/异常事件入库与后端 Trace 的联合查询，并核对跨服务 parent 上下文；不得以 G2 已通过的 `x-trace-id` 透传替代。

目标：让异常从检测、通知到 Trace 定位形成闭环，完成试点上线所需的权限、可靠性和运维准备。

| 周次 | 工作项 | 主要交付物 / 验收点 |
| --- | --- | --- |
| W21–W24 | 实现 Alert Engine 内置规则：Span error、延迟、Token / 成本、RAG 空召回；告警去重和状态流转 | 告警带规则、级别、服务、环境、Trace ID；支持确认、关闭和重新打开；可编辑规则阈值/窗口作为 P1 增强 |
| W24–W27 | 告警中心接真实 API；实现首批通知渠道（Webhook / 邮件优先）；支持告警到 Trace 的跳转 | 告警列表与通知渠道完成集成测试；通知失败可重试并可观测，不影响 Span 入库 |
| W26–W29 | 补齐项目隔离、角色最小权限、敏感字段策略、关键配置审计和服务接入配置 | 查询与写入权限分离；跨项目读取被拒绝；密钥轮换和撤销生效；默认不返回 Prompt / Response 原文 |
| W28–W30 | 平台自身健康与容量指标：Kafka lag、Collector 消费/写入失败、丢弃数、ClickHouse 查询耗时；压测与故障演练 | Kafka / ClickHouse 短时故障不拖垮业务；恢复后可继续消费；性能结果和容量基线归档 |
| W30–W32 | Staging 试点、用户验收、修复阻断问题、回滚演练和上线清单 | **阶段门 G3 / MVP**：需求文档 P0 验收项通过，项目方确认试点数据边界与上线观察人 |

### Phase 4：AI 根因分析与智能运维（第 32 周后，持续）

目标：在数据完整、权限和告警链路稳定后，再增加辅助分析与自动化能力。

- AI 根因建议：按 Trace 关联前端异常、服务端日志、RAG / LLM Span 和版本变化；输出证据与相关 Span，不自动修改业务系统。
- 智能运维：异常趋势分析、告警关联与处置建议；经人工确认后再考虑自动化修复。
- 成本优化：模型用量分析、路由与缓存建议；先做可解释报告，再逐步灰度策略。
- LangSmith 增强：Prompt 版本、评估数据集、离线评测和历史 Trace 回放。
- Sentry 增强：SourceMap、Issue 聚合、Release 对比和回归追踪。

## 5. 端到端关键路径与依赖

```text
Span / SDK 契约
   ↓
项目密钥与上报 API → Kafka Producer（traceId 分区键）
   ↓
Kafka ai-spans → Collector 校验 / 去重 / 批量写入 → ClickHouse 明细与聚合
   ↓                                                        ↓
Trace / 指标 / 告警查询 API ←────────────────────────────── 控制台真实数据
                         ↑
                Alert Engine 与通知渠道
```

关键依赖顺序：

1. 先确认统一 Span schema、环境和项目隔离规则，再并行开发 SDK、API 和 Collector。
2. 先打通 Kafka 到 ClickHouse 的最小事件，再做查询和仪表盘；避免 UI 先绑定未确定的数据口径。
3. Trace 查询依赖稳定的 `traceId / spanId / parentSpanId` 和 ClickHouse 排序键；AI 指标依赖模型与 RAG 属性约定。
4. 告警依赖可靠的 Span 消费和规则窗口；通知渠道依赖告警状态机，不应直接耦合业务请求线程。
5. Prompt / Response 相关能力必须等权限与脱敏策略通过评审后再排期，不因可视化需求放宽默认隐私策略。

## 7. 图片路线与需求优先级的对齐说明

图片路线图在 Phase 3 提到了 Prompt 管理和评估数据集，架构图也列出了 Sentry / LangSmith 的扩展能力；需求文档则将 Prompt 版本管理、评估数据集、Issue 聚合和 Release 对比列为 P2，将 SourceMap 和通知渠道列为 P1。本计划按需求表的优先级控制首期范围：

| 能力 | 需求文档优先级 | 本计划安排 | 是否阻塞 MVP |
| --- | --- | --- | --- |
| Trace / Span、LLM / RAG 核心指标、Trace 查询与详情 | P0 | Phase 1–2 | 是 |
| 告警列表与基础规则、确认/关闭、项目隐私配置 | P0 | Phase 3 | 是 |
| Webhook / 邮件通知、SourceMap、成本价格表、角色与审计增强 | P1 | Phase 3 按试点范围纳入，SourceMap 可后置 | 仅基础项阻塞 |
| Prompt 版本管理、评估数据集、Issue 聚合、Release 对比、AI 根因分析 | P2 | Phase 4 或 MVP 后续版本 | 否 |

如果业务方要求在第一版就提供 Prompt 管理或评估数据集，应作为范围变更单独评估数据权限、质量指标、工作量与试点时间，不挤占 G1/G2 的数据链路交付。

## 8. 人员与协作假设

当前排期假设一个小型跨职能团队：前端 1 人、后端 1–2 人（含数据链路）、测试 0.5–1 人，产品/项目协调 0.5 人；基础设施由后端或平台工程兼任。开发与测试可在契约稳定后并行，Kafka / ClickHouse 联调需要安排明确责任人。

| 工作流 | 主责 | 主要协作 |
| --- | --- | --- |
| 控制台、浏览器 SDK | 前端 | 后端提供契约与接入示例；测试覆盖浏览器错误和 Trace 透传 |
| API、TraceRecorder、项目配置 | 后端 | 前端联调；产品确认项目、服务、权限和隐私交互 |
| Kafka、Collector、ClickHouse | 后端/数据链路 | 测试验证重试、重复消息、故障恢复和 TTL |
| Alert Engine、通知 | 后端 | 前端实现告警处理；测试验证阈值边界及通知失败 |
| 试点验收与上线 | 产品/项目负责人 | 各模块主责、试点应用负责人、测试共同签字 |

若仅有 1 名前端和 1 名后端且无专职测试，建议按阶段上限（Phase 1/2/3 各 8/12/12 周）执行，或缩小首批接入范围；不建议同时承诺 SourceMap、Prompt 评估和 AI 根因分析。

## 9. 主要风险与缓解措施

| 风险 | 影响 | 缓解措施 / 触发时的调整 |
| --- | --- | --- |
| 项目/Span 契约在联调中变化 | SDK、Collector 与 ClickHouse 字段不兼容 | W1 冻结 schema v1；新增字段向后兼容，破坏性变化升 schemaVersion |
| Kafka 或 ClickHouse 短时不可用 | 监控数据积压或丢失，甚至影响业务 | 实现有界本地降级、重试和清晰丢弃计数；Collector 写库成功后再提交 offset；开展故障演练 |
| Trace 数据量和查询范围扩大 | 查询超时、ClickHouse 成本增加 | 限制查询时间范围与分页；按日期分区、排序键和 TTL；常用指标采用预聚合 |
| Prompt / 用户数据敏感 | 违规采集或跨项目泄露 | 默认关闭原文；先实现字段脱敏、权限校验和审计，未经评审不排原文采集 |
| AI 成本口径不一致 | 看板成本与账单不符 | 首期标注为估算；在价格表、缓存 Token、重试和折扣口径确认前不作为账单依据 |
| 小团队并行度不足 | Phase 2/3 与时间预期偏差 | 按 G1/G2/G3 里程碑滚动调整；P1/P2 后移，保留 P0 数据链路主线 |

## 10. 启动后的前两周建议

1. 确认首个试点 AI 应用、开发/测试环境、项目密钥流转方式和数据保留要求。
2. 基于 `packages/contracts` 对齐 Span schema v1、`projectId`、`environment`、时间戳单位、错误分类和 `x-trace-id` 透传约定。
3. 启动仓库 Compose 服务，验证 PostgreSQL 初始化、Kafka Topic 和 ClickHouse 表；记录当前 Collector 的端到端缺口。
4. 明确上报 API、Trace 列表/详情 API、指标和告警 API 的请求响应契约，作为前后端并行依据。
5. 先完成一条合成 Span 的 Kafka → Collector → ClickHouse 写入验收，再开始增加真实应用埋点。
