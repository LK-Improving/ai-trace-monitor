## 接口与口径

| 接口 | 返回内容 | 筛选口径 |
| --- | --- | --- |
| `GET /api/v1/metrics/overview` | summary/metrics、timeseries/series、services、recentErrors、topModels | 服务匹配整条 Trace；请求按有请求根的 Trace 去重；服务健康为 Span 级 |
| `GET /api/v1/metrics/ai` | llm 总量/模型分组、延迟、TTFT，rag 成功、空召回、召回/重排耗时 | 服务按调用 Span 筛选；LLM 仅 llm.generate、RAG 仅 rag.retrieve |

两个接口必填项目 UUID，环境默认 all，支持 dev/staging/prod；可选服务。时间采用 range=1h/24h/7d，或成对 UTC ISO Z from/to 半开区间，最多 30 天，两种模式不能混用。groupBy 仅支持 service。需求文档的项目成员 metrics:read RBAC 尚未实现，本轮采用既有平台管理员令牌保护；不会将令牌下发浏览器，也不扩大 Vite 读代理。

先按项目/环境/Trace/Span ID 使用确定性的 argMax 去重，再计算请求量和 Token；同一 Trace 多根只计一次，有任一错误子 Span 即计失败请求。无根链路和浏览器独立诊断不计请求，但无根 LLM 的 Token 仍计量。请求延迟取整链最早开始到最晚结束，不累加并行 Span。Token 只统计 llm.generate，即使根 Span 复制 model/usage 也不计入；模型名不规范时分组到 (unknown)。

分位数在 ClickHouse 内精确聚合，时间趋势补零；不把全部明细加载到 API 内存计算。AI 耗时样本严格检查 JSON、数值类型和合法范围；缺失或非法属性不补成零样本。RAG 空召回率分母为成功且召回数量可观测的调用数，零分母返回 null，避免误称“没有空召回”。TTFT/召回/重排样本数单独返回，零样本耗时值为零仅是接口约定。

聚合响应不含 Prompt、回答、文档正文/URL、原始异常、向量或任意 attributes。项目/环境/时间/服务均绑定参数；400/401/404/503 为有限、脱敏错误。模型最多 100 组，总览服务/趋势有结果数量上限；超限返回 503，而不是假完整结果。复用 W13 的查询读取/内存/执行预算。

## 与架构图片的实现取舍

图片中的物化视图与持久化长周期聚合未在本轮落库。当前 Collector 至少一次投递，直接对原始插入块累加会把重投递算两次；本轮先完成去重读取聚合并记录性能基线。后续持久化预聚合需设计跨批幂等、迟到 Span、重复版本和 TTL 后的长期指标口径，不能仅添加累加视图就宣称正确。[ClickHouse 官方说明](https://clickhouse.com/blog/postgres-to-clickhouse-data-modeling-tips-v2)指出增量视图只看到当前插入块，重复版本会导致重复计数。

JSON 数值提取与类型判断参考 [ClickHouse JSON Functions](https://clickhouse.com/docs/reference/functions/regular-functions/json-functions)。采用有界 SQL 查询而不是返回原始 JSON，让类型过滤和敏感信息投影在聚合边界完成。

旧 `/overview` 为现有首屏保留，仍为旧统计口径；新接口的去重请求/错误语义与旧口径不同，页面切换时应整体迁移。查询只看时间窗内已入库数据，跨窗、丢失或尚未入库的节点会造成不完整；多个聚合查询没有共享事务快照，持续入库时总量与分组可能短暂不一致，不以跨查询求和相等作为可用性的强约束。

## 验收方式

脚本 `scripts/w15-metrics-acceptance.cjs` 使用随机隔离项目、Topic/消费组和自有进程；沿用六种本地 OpenAI/Qdrant 协议调用，真实经过 API → Kafka → Collector → ClickHouse，再执行实际 HTTP 聚合查询。不调用付费模型，不证明真实 Qdrant 检索质量。Collector 使用构建产物，原有 tsx watch 问题不在本轮修复。

性能数据集：10,000 条请求，每条含 http.server、rag.retrieve、rag.recall、rag.rerank、llm.generate 五个 Span，共 50,000 个唯一 Span，额外重复 1,000 行；数据分布在最近小时、日和周，3 个模型。根节点故意复制 Token/model，10% 检索失败，成功中的可观测空召回计数独立，半数 TTFT 为有效数值，另一半是非法字符串。另有小型隔离坏属性/模型名投影测试。

测量对象：1h/24h/7d 的列表、总览、AI 三类 HTTP 查询，每个组合预热后 20 次串行测量，P95 使用 nearest-rank；包含 HTTP、鉴权、PG 项目检查、ClickHouse 查询、序列化，非仅 SQL 时间。应用无结果缓存，ClickHouse/操作系统暖缓存未禁用。列表 P95 < 2 秒、总览 P95 < 3 秒为排期目标；AI 也使用 3 秒本地基线。数据量和并发明确限定，结果不是生产容量认证或百万行/并发 SLO。

执行命令：全仓 build/typecheck；构建后运行 API、Web、contracts、Collector、relay 测试；设置 TRACE_OPS_RUN_INTEGRATION=1 后运行本轮脚本。结果和清理状态保存在 `output/acceptance/w15-metrics-result.json`。只清理本次项目 UUID/slug、CH 行、自有 Topic/消费组和进程，不删除共享卷或用户数据。

### 问题发现

P0：无。

P1：发现并修复以下问题，复查通过：

- ClickHouse JSONType 小数类型实际为 Double，原 Float64 判断漏计所有小数 TTFT/召回/重排样本。通过实际 ClickHouse 查询定位，修正类型判断，并重新验证 2 个 TTFT、6 个召回、6 个重排样本。
- 总量与模型分组分别读取，持续入库时可能不同步，强制求和一致会误报 503。改为独立校验并明确无事务快照保证。
- environment=all 时，跨环境相同 Trace ID 被错误当成重复错误项。改用 environment + traceId 标识，错误摘要带环境且排序增加环境维度。
- Token 的 UInt64 SUM 可能先溢出再通过 JavaScript 安全整数检查。共同查询先提升至 UInt128，再校验输出；用两行 2^63 Token 的真实存储测试验证总览/AI 均安全 503，不返回回绕后的假小值。
- 长于 7 天的合法自定义窗口缺少六小时桶白名单，补齐并覆盖 30 天边界。

P2：统一两类接口模型标识规则；补充属性 16 KiB 上限、召回数有限/整数/0–100 校验；修正草稿测试中 LIMIT 20 与 LIMIT 2001 的误匹配、缺失环境 fixture；验收脚本使用独立结果文件，不改写 W13 历史证据。无剩余阻塞本轮的问题。
