# W21–W24 内置告警与处理闭环验收

日期：2026-10-03

范围：Phase 3 W21–W24 内置规则、告警 API、控制台告警中心和 Trace 跳转。本地 Compose Postgres、Kafka、ClickHouse 均保持运行。

## 交付内容

- Collector 新增四条固定规则：Span 错误（critical）、单 Span 耗时 `> 2,000ms`、单次 `llm.generate` 总 Token `> 5,000`、成功 `rag.retrieve` 的明确零召回。RAG 零召回可由 `rag.recalled_count=0`、`retrievedCount=0` 或空 `sources` 数组表示；缺少计数/来源信息不会误报。Token 是用量代理，不代表货币成本。
- PostgreSQL 新增告警事件与 occurrence 唯一键账本；API 和 Collector 启动时在共享 advisory lock 下幂等应用迁移，覆盖已有 Compose volume。并发初始化已用真实 PG 验证。
- 同一项目/环境/服务/规则聚合事件；新 occurrence 更新首次/最近时间和触发次数，重复 occurrence 不重复计数。状态支持 active → acknowledged → resolved，以及受 scope 冲突检查的 resolved → active。
- 新增受 `AdminTokenGuard` 保护的列表、汇总和状态 API。浏览器仍只经同源 allowlist 代理访问，管理员凭证留在服务端。
- 告警页接入真实 API，提供项目/环境、状态/级别筛选、分页、汇总、确认/关闭/重新打开和关联 Trace 跳转；包含加载、失败重试与空态。固定规则说明与服务端条件一致。

## 投递与存储语义

Collector 顺序为：先提交 PG occurrence/告警事务，再写 ClickHouse，最后提交 Kafka offset。PG 失败不会写 ClickHouse 或推进 offset；ClickHouse 失败时 offset 保持未提交，重放由 PG occurrence 唯一键吸收。ClickHouse 使用 topic、partition 和该批次 offsets 生成稳定 dedup token；Collector 启动时为现有 MergeTree 表设置有限去重窗口，同一 insert token 的实际重复写入已在容器中验证只落一行。

该 ClickHouse token 保证的是相同 Kafka 批次的重试，不是跨不同 offset 的相同业务 Span 合并。相同业务 Span 以新 offset 再上报时，PG 告警账本不会重复触发；Trace 查询仍按 Span ID 去重。
